# はじめに

大規模なアプリケーションを作っているとファイル同士の依存関係が複雑になってしまうことはよくあることだと思います。下記は典型的な大規模プロジェクトでの苦悩あるあるだと思います

- 何度もパッケージのimportルールについて指摘を行っている
- 禁止されたパッケージの依存が目が滑ってマージされてしまった

こことここのパッケージは依存してはいけないのようなコーディングルールを決めて運用しているところが多いかなと思っていますが、その運用確実に守れていますでしょうか？

そんなときは**物理的**に参照できなくすればいいのです。

# Gradleマルチプロジェクトとは

Gradleのマルチプロジェクトとは、簡単に言うと「1つの大きなプロジェクト（ルート）の中に、複数の小さなプロジェクト（サブプロジェクト）を同居させる仕組み」です。

各サブプロジェクトは自分自身のビルド設定（build.gradle）を持ち、独立したモジュールとして機能します。それでいて、ビルド自体はルートプロジェクトのプロセスとして一括で統合して扱うことができるのが特徴です。
(もちろん独立してビルドプロセスを実行することも可能です。)

この仕組みの最大のメリットは、サブプロジェクト間の依存関係をコンパイルレベルで厳密に制御できる点にあります。
たとえば、「インフラ層のモジュールはドメイン層に依存できるが、ドメイン層からはインフラ層を呼び出せない」といったように、ビルドファイルに依存関係を明示することで、アーキテクチャ上のルールをコンパイルエラーとして物理的に強制できるようになります。

# なぜクリーンアーキテクチャと相性がいいのか

先程述べたようにマルチプロジェクト構成にすることにより、依存関係をビルドファイルによって明示しコンパイルレベルでルールを強制できるようになります。

ではなぜこれがクリーンアーキテクチャと相性がいいのでしょうか？

DDDの戦術パターンで広く用いられている、クリーンアーキテクチャ・オニオンアーキテクチャ・レイヤードアーキテクチャは共通して「関心の分離と依存性のルール」に主眼が置かれています。

![クリーンアーキテクチャ](/images/81edee7e050559/CleanArchitecture.jpg)
*[The Clean Code Blog - by Robert C. Martin (Uncle Bob)](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)*

上記は至るところでこすられているクリーンアーキテクチャの依存関係図です。

依存関係はこの中心に向かっていく方向でしか許可されていません。
しかしながら単一プロジェクトでこれらのレイヤーを管理するとIDEのインポート機能などで簡単に逆方向の依存関係が作成できてしまいます。

コンパイルレベルで保証することでIDEからの手軽なインポートを防ぐことができるうえ、万が一そこが突破されたとしてもbuild.gradleに不穏な変更が現れるので、単純なインポートよりも遥かにレビューで防ぎやすくなります。

# プロジェクト具体例

## プロジェクト全体像

```:text
gradle-root-project/  <-- settings.gradle.kts で全サブプロジェクトを管理
│
├── build.gradle.kts     <-- 共通ビルド設定
├── settings.gradle.kts
│
├── domain/              <-- 【Domain層】（Core logic: Entities, Interfaces）
│   ├── build.gradle.kts
│   └── src/main/kotlin/com/example/domain/
│       ├── entities/
│       └── repositories/
│
├── usecase/             <-- 【Use Case層】（Application logic: Interactors）
│   ├── build.gradle.kts  
│   └── src/main/kotlin/com/example/usecase/
│       └── interactors/
│
├── interface-adapter/   <-- 【Adapter層】（Presenters, Controllers）
│   ├── build.gradle.kts
│   └── src/main/kotlin/com/example/adapter/
│       ├── controllers/
│       └── presenters/
│
├── infrastructure/    <-- 【Infrastructure層】（DB Implementation, External API）
│   ├── build.gradle.kts
│   │
│   └── src/main/kotlin/com/example/infra/
│       └── persistent/
│           └── DbRepositoryImpl.kt
│
└── app/               <-- 【DI/Assembly層】（Entry Point, Main Application）
    ├── build.gradle.kts
    │
    └── src/main/kotlin/com/example/app/
        └── Application.kt
```

## 各ビルドファイルの記述例

上記の構成を実現するためのビルドファイルの例です。プロジェクト間の依存方向が明確に制限・定義されていることがわかります。

### ルートプロジェクトの設定

**settings.gradle.kts**（全サブプロジェクトの読み込み）

```:kotlin
rootProject.name = "gradle-root-project"

include(":domain")
include(":usecase")
include(":interface-adapter")
include(":infrastructure")
include(":app")
```

**build.gradle.kts**（共通設定）

```:kotlin
plugins {
    kotlin("jvm") version "1.9.20" apply false
}

allprojects {
    repositories {
        mavenCentral()
    }
}

subprojects {
    apply(plugin = "org.jetbrains.kotlin.jvm")

    dependencies {
        // 全サブプロジェクト共通の依存（テストライブラリなど）
        testImplementation(kotlin("test"))
    }
}
```

### サブプロジェクトの設定

**domain/build.gradle.kts**
もっとも内側のレイヤーであるため、他のプロジェクトには一切依存しません。
```:kotlin
dependencies {
    // 他プロジェクトへの依存なし
    // （外部ライブラリへの依存も最小限にとどめる）
}
```

**usecase/build.gradle.kts**
Domain層にのみ依存します。
```:kotlin
dependencies {
    implementation(project(":domain"))
}
```

**interface-adapter/build.gradle.kts**
UseCase層（および必要に応じてDomain層）に依存します。
```:kotlin
dependencies {
    implementation(project(":usecase"))
}
```

**infrastructure/build.gradle.kts**
Domain層やUseCase層で定義されたインターフェースを実装するため、それらに依存します。
```:kotlin
dependencies {
    implementation(project(":domain"))
    implementation(project(":usecase"))
    
    // DBや外部APIクライアント等のライブラリ
    // implementation("org.postgresql:postgresql:42.6.0")
}
```

**app/build.gradle.kts**（エントリーポイント）
すべてのモジュールを組み立てて（DIなど）実行するため、各プロジェクトに依存します。
```:kotlin
dependencies {
    implementation(project(":domain"))
    implementation(project(":usecase"))
    implementation(project(":interface-adapter"))
    implementation(project(":infrastructure"))
    
    // Webフレームワーク（Spring Boot等）などの依存
}
```

## ライブラリの管理カオスになりそう -> Version Catalogで解決

Version Catalogを使うと、`gradle/libs.versions.toml` という一つのファイルでプロジェクト全体のライブラリとそのバージョンを一元管理できるようになります。

**gradle/libs.versions.toml の例**
```:toml
[versions]
kotlin = "1.9.20"
ktor = "2.3.5"

[libraries]
ktor-server-core = { module = "io.ktor:ktor-server-core", version.ref = "ktor" }
```

**各サブプロジェクトの build.gradle.kts での呼び出し**
```:kotlin
dependencies {
    // バージョン番号やパッケージ名を直接書かず、カタログから型安全に呼び出す
    implementation(libs.ktor.server.core)
}
```

このように設定することで、以下のメリットが得られます：

- **バージョンの一元管理**: 全てのサブプロジェクトがカタログで定義された同じバージョンのライブラリを使用することになるため、モジュール間でのバージョン不整合を防ぐことができます。
- **依存関係の可視化**: プロジェクト全体でどんな外部ライブラリが使われているかが `libs.versions.toml` を見るだけで一目で把握できます。
- **安全なアップデート**: ライブラリのバージョンを上げる際は、カタログファイルの `[versions]` ブロックを1箇所書き換えるだけで、それを利用している全サブプロジェクトに一斉に適用されます。

このように、マルチプロジェクト構成とVersion Catalogを組み合わせることで、アーキテクチャの強制力を高めつつ、ライブラリ管理のメンテナンス性も高く保つことができます。
