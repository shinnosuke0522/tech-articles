# はじめに

皆さんテストコードをどのように関していますでしょうか？
まとめて管理していて、テストの責務が曖昧になったテストコードが実装されたり、テストの実行を分けられなくてCIが遅くなったりしたことはないでしょうか？

そんなときは**物理的に**境界を分けてしまえばいいのです。

本記事では、各テスト種別の定義や実行コスト・メンテナンスコストを改めて整理し、その観点からテストコードを物理的に分割するメリットについて解説します。

# テスト種別について

皆さんは単体テスト、結合テストと聞いてその役割を的確に答えられますか？

正直結構怪しかったり、人によって定義が違うなんてこと結構あるのではないでしょうか？

事実私が観測している範囲でも定義がかなり人によって異なります。なので先にそれらを明確にします。

各テストの種別と定義、および責務範囲は以下の通りです。

### UnitTest（単体テスト）
- **スコープ**: 
  - 最小実行単位（関数、メソッド、単一クラス）
  - Webフレームワークを含めず、純粋なロジックのみ
  - 基本的にはドメイン層のコードのテストになる
- **外部依存**: 
  - すべてモック/スタブ化し、オンメモリで完結させる
- **担保する価値**: 
  - ビジネスロジックの分岐
  - アルゴリズムの正確性

![ユニットテストの責務範囲](/images/970e57aed6c1b1/UnitTestResponsibility.png)

### IntegrationTest（結合テスト）

- **スコープ**: 
  - アダプター層（DBリポジトリ、Webコントローラー等）
  - 必要に応じてフレームワークの一部もスコープに含める。
- **外部依存**: 
  - 対象が対象システムの管理下にある場合（DBなど）は本物を使う
  - システム外の連携先のみ、Mock Server（WireMockなど）を用いて動作をエミュレートする
- **担保する価値**: 
  - コンポーネント同士が正しいプロトコル/データ構造で通信できていること
  
![結合テストの責務範囲](/images/970e57aed6c1b1/IntegrationTestResponsibility.png)

### ComponentTest（コンポーネントテスト）
- **スコープ**: 
  - 1つのデプロイ可能なサービスやコンポーネント単体
  - Webフレームワークを起動し、APIとしてリクエストを受け付ける状態。
- **外部依存**: 
  - 対象が対象システムの管理下にある場合（DBなど）は本物を使う
  - システム外の連携先のみ、Mock Server（WireMockなど）を用いて動作をエミュレートする
- **担保する価値**: 
  - アーキテクチャの境界内で業務要件（API仕様等）が満たされていること
  
![コンポーネントテストの責務範囲](/images/970e57aed6c1b1/ComponentTestResponsibility.png)

### E2E Test（エンドツーエンドテスト）
- **スコープ**: 
  - システム全体（UI/Frontend 〜 Backend 〜 DB 〜 外部連携）
  - 本番環境と同等のフルスタックを対象とする。
- **外部依存**: 
  - モックなし
  - または商用決済API等、真に必要なもののみダミー化
- **担保する価値**:
  -  実際のユーザーシナリオ通りにシステム全体が動くことの証明

# テストのメンテナンスコスト

IntegrationTestやComponentTestなどテストは上位の概念になればなるほど、以下のような課題を抱えることになります。

- **実行時間が遅い**: Webフレームワークの起動やデータベース（Testcontainersなど）の立ち上げに時間がかかる。
- **壊れやすくメンテが大変**: DBの事前データ（Fixture）の準備が複雑化します。さらに、結果の期待値を巨大なJSONファイルなどで管理している場合、カラムが1つ増えただけで無関係な大量のテストが割れ、メンテナンスコストが跳ね上がります。
- **バグの特定が困難**: テストが落ちた際、「ロジックが悪い」のか「外部環境が悪い」のかの切り分けに時間がかかる。

一方で、すべてをモック化してオンメモリで動くUnitTestは、ミリ秒単位で爆速に動作し、壊れた原因もピンポイントで特定できるため、メンテナンスコストが極めて低く済みます。

様々な記事で引用されているテストピラミッドの概念は、この特性と向き合っていくうえで生み出されたプラクティスです。

![テストピラミッド](/images/970e57aed6c1b1/TetsPyramid.png)

このようなテスト種別ごとの特性を踏まえたうえで、適切に管理する必要があります。
メンテナンスコストが高いテストが膨れ上がると、その修正コストが実装にはねてきます。テストがボトルネックとなってしまっては本末転倒なので、テスト量も意識すべきだと考えます。

# テストコードの適切な管理方法（物理的な分離）

結論から言うと、**テスト種別ごとにディレクトリやモジュールを物理的に分離する**のが良いと考えます。

前述したように、テスト種別ごとに「依存関係の扱い方」「実行コスト」「メンテナンスコスト」は大きく異なります。これらをすべて同じディレクトリに混在させてしまうと、境界が曖昧になり、冒頭であげたような問題を引き起こします。

テスト種別ごとに物理的な境界を設けることで、大きく2つの課題を解決できます。

**1. 依存関係の隔離（クリーンな状態の強制）**
UnitTestは外部依存（DBやフレームワーク等）を一切持たない純粋なロジックを対象とします。これをIntegrationTestなどのインフラに依存するコードと物理的に分けることで、誤ってUnitTest内にDBアクセスや重いライブラリの依存が紛れ込むのを防ぎ、「いつでもミリ秒単位で爆速に実行できる」クリーンな状態を強制できます。

**2. 実行コストの隔離（CI実行タイミングの制御）**
IntegrationTestやComponentTestは、TestcontainersによるDB起動やフレームワークの初期化を伴うため、どうしても実行時間が長くなります。これらを物理的に分離しておくことで、CI上で「PR作成時は爆速なUnitTestとIntegrationTestのみを回す」「時間のかかるComponentTestはmainマージ時や夜間にのみ実行する」といった、**開発スピードを落とさないための柔軟な実行制御**が容易になります。

このように、単にテストを書くだけでなく、特性の異なるテストの「境界」を物理的に分けることこそが、破綻しないテスト戦略の第一歩なのです。
